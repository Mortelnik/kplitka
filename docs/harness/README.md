# Минимальный harness индивидуального проекта

## Назначение

Единый способ выдать задачу, проверить локальный результат и передать его
на ревью. Это не автономный оркестратор, не новый агентный runtime и не
полноценный стенд оценки 40+ запросов.
Дедлайн проекта: 19 декабря 2026 года.

Harness не вызывает модели, не отправляет данные в сеть, не меняет ветки,
не создаёт issues и не делает commit/push/merge.
Он запускает фиксированные локальные команды и сохраняет их результаты.
Сами проверки запускают код проекта: изоляцию и права нужно обеспечивать
на уровне среды, а не считать этот скрипт безопасной песочницей.

## Быстрый запуск на Windows

Из `D:\Projects\kalitka-kp-plugin`:

```text
uv sync --extra dev
uv run python scripts/check.py --list
uv run python scripts/check.py
```

На Linux/macOS команды те же. У скрипта нет зависимости от Bash.
`--list` только показывает проверки, не запускает их и не пишет файлы.
Первую установку зависимостей выполняйте с разрешения владельца.

Проверки:
1. `python -m ruff check src scripts tests plugins`
2. `python scripts/validate_package.py`
3. `python -m pytest -v`

Интерпретатор берётся из текущего окружения, корень определяется по скрипту,
а не по текущей папке терминала. Команды не берутся из задачи или промпта.
Таймаут каждой проверки 600 секунд; изменить можно `--timeout-seconds N`.
Запуск продолжается после ошибки, чтобы собрать все три результата.

## Отчёт

Каждый запуск создаёт уникальную папку `out/checks/<UTC-time>-<id>/`:

```text
report.json
lint.log
package.log
tests.log
```

JSON содержит команды, коды завершения, время, путь окружения, сведения
о Git до/после и локальные пути логов. Нет Git — это явная отметка,
а не утверждение о чистой ветке.
Код завершения скрипта 0, если все проверки прошли; 1 при неуспехе проверок,
2 при ошибке самого harness. Таймаут проверки записывается как 124,
невозможность запустить команду как 127.

Логи могут содержать данные, выведенные тестами. Не запускайте проверки
на реальных клиентских данных и не публикуйте логи без просмотра.
`out/` уже исключён из Git. Файлы не загружаются куда-либо автоматически.

## Роли ваших агентов

Ниже рекомендации для запуска, не результаты сравнительного теста моделей.
Размер Qwen2.5-Coder, квантование, контекст и привязка моделей к GPU пока
не уточнены. Не считайте RTX 5080 гарантией лучшего ревью.

| Агент, как указан владельцем | Начальная роль | Ограничения |
|---|---|---|
| Qwen2.5-Coder («qwen coder 2.5») | Небольшие функции и тесты по готовому контракту | Один компонент за задачу; без самостоятельного изменения архитектуры |
| Qwen3 8B | Проверки по бинарному чек-листу, поиск несогласованностей, проект тестовых случаев | Не единственный проверяющий денежных правил; спорные выводы перепроверять |
| Агент заказчика на «GPT Sol 6», доступ через Astra/Codex | Интеграция, ревью сложных изменений, разбор блокеров и контрактов | Название модели и интерфейсы указаны со слов владельца; качество подтверждать результатами |
| Владелец | Бизнес-решения, эталоны, доступы и приёмка | Не перекладывать на модель утверждение скидок и допуск реальных материалов |

Роли можно менять по результатам небольших проверяемых задач.
Ревью, сделанное другой моделью, не становится автоматически независимым
эталоном и не заменяет приёмку владельцем.

## Общий процесс

1. Скопируйте `templates/TASK.md`, заполните задачу и заморозьте критерии.
   Незакрытые Q1–Q9 вынесите в блокеры, а не разрешайте агенту их придумывать.
2. В контракте укажите разрешённые файлы, запрещённые действия и базовый commit.
3. Выдайте задачу одному разработчику в отдельной рабочей папке/ветке.
4. Он выполняет harness и заполняет `templates/IMPLEMENTATION_REPORT.md`.
5. Передайте diff, контракт и отчёт другому агенту, который заполняет
   `templates/REVIEW_REPORT.md` без редактирования кода.
6. Исправления выполняет разработчик. После исправлений harness запускается заново.
7. Владелец проверяет результат и разрешает commit/merge отдельно.

Изменение кода после проверки делает прежний отчёт историческим:
перед слиянием нужна новая проверка. Harness фиксирует Git-состояние, но не
блокирует параллельные правки и не гарантирует соблюдение контракта.
Работайте без других пишущих агентов в этой папке.

## Стартовые сообщения

Разработчику:

```text
Прочитай AGENTS.md и контракт задачи <путь>.
Подтверди ветку, разрешённые файлы и критерии.
Реализуй только эту задачу. При блокере остановись, не угадывай правила.
Запусти scripts/check.py и заполни IMPLEMENTATION_REPORT.
Не делай push/merge и не меняй чужие файлы.
```

Ревьюеру:

```text
Прочитай AGENTS.md, контракт, diff и IMPLEMENTATION_REPORT.
Не редактируй код. Проверь разрешённую область, смысл тестов,
деньги, UTF-8 и соответствие критериям.
Для каждого замечания укажи файл/строку и способ воспроизведения.
Заполни REVIEW_REPORT. Не объявляй работу принятой за владельца.
```

Оба агента читают инструкцию явно: автоматическое обнаружение AGENTS.md
в каждом конкретном клиенте ещё не проверено.

## Параллельные машины и среды

На разных компьютерах используйте отдельные клоны и ветки.
Worktree одного локального репозитория не является способом связать разные ПК.
На одной машине допустимы отдельные worktree. Для каждой рабочей папки
создаётся собственное окружение; `.venv` не копируется между машинами.
Общий контракт редактирует только назначенный агент.

Для Hermes сначала проверьте tool calling и выполнение тестовой команды.
Если модель не умеет надёжно пользоваться инструментами, поручайте ей
анализ предоставленного diff, но не фиктивное «выполнение» проверок.
Фактические команды должны оставлять реальные логи.

## GitHub и существующие проверки

На приватном Free-репозитории ревью остаётся правилом команды.
Не выдавайте отчёт агента за технически обязательный внешний approval.
Работающий workflow CI можно оставить. Чтобы использовать одну команду в CI,
в отдельном PR замените шаги validator/pytest на:

```text
python scripts/check.py
```

Установка `pip install -e ".[dev]"` должна остаться перед этим шагом.
Workflow этим дополнением автоматически не заменяется.

## Граница качества

Существующие проверки каркаса не доказывают корректность контейнеров,
скидок, налогов и логистики. Они становятся проверенными только по мере
добавления согласованных бизнес-тестов. Финальные 15+ запросов не выдаются
разработчику до замороженного итогового прогона.
Полноценный eval-runner, метрика 80% и сравнение с базовой моделью остаются
отдельными задачами проекта; этот harness их не подменяет.

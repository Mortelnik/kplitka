### 0.1. Формат персонального ТЗ
Каждый раздел роли содержит:
- **Цель роли** — законченный результат, который человек обеспечивает.
- **Границы** — что делает сам, что получает от других, чего не делает.
- **Задачи** — идентификатор, действие, результат, срок (неделя), критерий приёмки.
- **Входы и выходы** — форматы, обязательные поля, поведение при ошибке.
- **Зависимости** — от кого и когда нужны материалы; заглушки для работы без ожидания.
- **Приёмка** — воспроизводимый сценарий, ожидаемый результат, кто проверяет.

### 0.2. Разделение «требование ТЗ» и «решение команды»
Обязательное из исходного ТЗ: программный расчёт сумм, точная денежная арифметика, источники фактов, 80% метрика, второй профиль, комплект сдачи. Проектные решения команды (названия модулей, конкретная библиотека шаблонизации, структура JSON) — фиксируются в общей схеме данных на неделе 1 и не меняются без решения тимлида.

### 0.3. Общие контракты команды (согласовать на неделе 1)

| Объект | Что фиксируется |
|---|---|
| **Профиль компании** | Идентификатор, каталог, прайс, правила, кейсы, шаблон DOCX, происхождение данных и источники фактов |
| **Потребности клиента** | Отрасль, задача, масштаб, бюджет, ограничения; неизвестные значения и противоречия помечаются явно |
| **Результат подбора** | Идентификаторы продуктов, количество, период, обоснование, ссылки на факты, открытые вопросы |
| **Результат расчёта** | Строки, цены, скидки, налоги, суммы, валюта, правило округления, версия использованного прайса |
| **Данные для документа** | Потребности, решение, обоснование, проверенный расчёт, известные условия |
| **Служебная сводка** | Источники, допущения, нерешённые вопросы |

Это внутренние контракты команды. Способ вызова инструментов клиентом Kalitka AI и формат пакета подтверждает Р1 на неделе 1 — до этого интеграционные интерфейсы считаются черновиками.

**Железное правило:** текст в чате и DOCX получают суммы из одного структурированного результата расчёта, а не вычисляют их независимо.

### 0.4. Границы задачи из исходного ТЗ
- ФИО, телефоны и паспортные сведения клиентов не являются входом проекта; подключение CRM не требуется.
- КП всегда остаётся черновиком для проверки сотрудником; автоотправка не входит в проект.
- При использовании реальных материалов условия доступа согласуются до их получения; синтетические цены и достижения явно помечаются.

### 0.5. Правила работы
- Один компонент — один владелец; проверяющий всегда другой человек.
- У каждой задачи есть конкретный выход (артефакт), а не «изучить».
- Каждый работает от заглушек, не ожидая готовности чужих компонентов.
- Критерии и эталоны готовятся вместе с данными, QA не оставляется на конец.
- Финальный набор из 15+ запросов физически отделён и не используется при отладке; первый итоговый прогон фиксируется, повторные результаты после исправлений показываются отдельно.
- **Таблица перераспределения (раздел 6) заменяет все упоминания отсутствующих Р4/Р5** — включая проверяющих и поставщиков входных материалов.

### 0.6. Общий стек и рамки (предложение команды)

- **Стек:** Python 3.11+, pytest, pydantic (валидация), python-docx + docxtpl (документы), jsonschema (контракты); репозиторий на GitHub с Projects и ревью PR.
- **Разделы «Предлагаемые подходы и методы» в каждой роли — предложения, а не требования исходного ТЗ.** Конкретные решения фиксируются после согласования Р1.1; окончательный алгоритм расчёта — после закрытия открытых вопросов бизнеса (Q1–Q9 в правилах профиля).
- Поддержку function calling и structured output в предоставленном API проверять на месте в первую неделю; параметры Chat Completions не переносить на Responses API наугад.
- Из болванок профиля не наследовать неподтверждённые параметры (термин FCA, тип HC, включённость НДС в цену) как решения.
- СПАРК и автозаполнение карточки — вне критического пути: базовый путь — ручная карточка компании.

## 2. Р2 — Python-разработчик: данные и расчётное ядро

### Цель роли
Программные инструменты проверки профиля компании и расчёта КП с автоматическими тестами — то, что гарантирует достоверность сумм и жёстких ограничений.

### Границы
- **Делает:** загрузку и валидацию данных, расчётный движок, тесты, поддержку второго профиля.
- **Не делает:** промпты и тексты (Р3), оценку качества КП (Р4), упаковку в клиент (Р1).
- **Важно:** эталон для теста нельзя получать той же функцией, которую проверяют. Эталоны готовит Р4 независимо.

### Задачи

| ID | Задача | Результат | Срок | Критерий приёмки |
|---|---|---|---|---|

### Предлагаемые подходы и методы (не требование ТЗ)

| Метод | К каким задачам | Минимальный пример | Проверка результата |
|---|---|---|---|

| Неизвестный тариф доставки — не ноль: результат разделяет товар, известные расходы и расходы, требующие уточнения | Р2.4 | итог: товар + «доставка требует расчёта» | Товарный итог не выдаётся за доставку до склада |
| Тесты: pytest + параметризация из requests.csv/JSONL; границы: ровно контейнер, чуть меньше/больше, 4 и 5 контейнеров, день достижения года, границы сезона, весь/неполный остаток, обновление прайса | Р2.9 | `@pytest.mark.parametrize` по эталонам | Все ветки покрыты, включая негативные |

### Входы и выходы
- **Входы:** форматы контрактов (Р1.2), основной профиль (Р4), эталонные расчёты (Р4), запросы на расчёт от слоя Р3/Р1.
- **Выходы:** валидатор профиля; движок расчёта; схема результата расчёта; тесты.
- **До готовности данных Р4:** работает от мини-профиля на 3–5 позиций (заглушка недели 1–2).

### Приёмка роли
Все контрольные суммы совпадают с независимыми эталонами; превышенная скидка и неизвестный продукт не проходят как допустимое предложение; после обновления прайса используются новые цены. Проверяет: Р4 (эталоны) и Р1 (сквозной сценарий).

## 3. Р3 — Разработчик LLM/DOCX: пользовательский сценарий

### Цель роли
Путь от запроса клиента до обоснованного черновика КП в чате и редактируемого DOCX-документа по шаблону.

### Границы
- **Делает:** извлечение потребностей, уточняющие вопросы, подбор и формулировки, шаблон DOCX, сборку документа, служебную сводку.
- **Не делает:** расчёт сумм (только Р2), оценку собственного качества (Р4), установку пакета (Р1).
- **Контроль выдумывания:** существенные утверждения не просто имеют ID источника — реальный текст должен соответствовать содержимому источника. Это проверяется на сценариях, в том числе вручную.

### Задачи

| ID | Задача | Результат | Срок | Критерий приёмки |
|---|---|---|---|---|
| Р3.0 | После технического probe недели 1 собрать бизнес-прототип недели 2: запрос → подбор → программный расчёт → DOCX; smoke-документ не заменяет КП | Рабочий бизнес-сценарий на небольшом профиле | Нед. 2 | Демо в целевом клиенте использует ядро и профиль, а не синтетические числа smoke |
| Р3.1 | Извлечение структурированных потребностей из запроса (по контракту «Потребности клиента») | Модуль извлечения + промпты | Нед. 4 | На 10 примерах поля заполнены верно; неизвестное помечено, а не угадано |
| Р3.2 | Конкретные уточняющие вопросы при нехватке сведений | Логика уточнений | Нед. 4 | Вопросы относятся к делу; не спрашивает то, что есть в запросе |
| Р3.3 | Обработка противоречий, недостаточного бюджета, отсутствующего продукта | Сценарии отказа и альтернатив | Нед. 4 | Объясняется причина + предлагаются допустимые варианты; изменение исходных требований помечено явно |
| Р3.4 | Подбор продуктов и релевантных кейсов из материалов профиля | Механизм подбора | Нед. 4 | Подбор только из каталога; кейсы релевантны задаче |
| Р3.5 | Передача выбранных позиций в расчётный инструмент Р2; текст КП строится на подтверждённых материалах | Промпты генерации текста | Нед. 4–5 | Неподтверждённые функции, сроки, гарантии, результаты не попадают в текст |
| Р3.6 | Шаблон DOCX: задача клиента, решение, состав, обоснование, расчёт, известные условия | Шаблон документа | Нед. 2 (минимальный), нед. 5 (финал) | DOCX редактируется и корректно открывается; суммы вставлены из результата Р2 |
| Р3.7 | Служебная сводка: источники, допущения, нерешённые вопросы | Сводка отдельным блоком/файлом | Нед. 5 | Сводка не смешивается с текстом КП |
| Р3.8 | Пересборка документа после уточнений пользователя | Цикл «уточнение → пересборка» | Нед. 5 | После уточнения документ собирается с новыми данными |
| Р3.9 | Черновик КП в чате (структура и форматирование) | Формат черновика | Нед. 5 | Черновик отражает тот же расчёт, что и DOCX |
| Р3.10 | Технически корректные примеры КП и сведения о сценарии — передаются Р5 для итоговой подборки и пользовательской документации | Материалы для Р5 | Нед. 6 | Примеры соответствуют отчёту Р4; итоговую подборку собирает Р5 |
| Р3.11 | Проверить активацию skill: прямой и косвенный запрос, неполный запрос, смежный нецелевой запрос, невозможные условия | Таблица 5 типов сценариев с исходными ответами | Нед. 2 | Skill не выдумывает ассортимент/стаж/условия; нецелевые запросы не вызывают расчёт; незаполненные правила ведут к уточнению |

### Предлагаемые подходы и методы (не требование ТЗ)

| Метод | К каким задачам | Минимальный пример | Проверка результата |
|---|---|---|---|
| Извлечение потребностей: structured output по схеме (если поддержка подтверждена в API); `null` вместо угадывания; JSON проверяет код | Р3.1 | «хочу 20 т» → `{"product_ids": null, "quantity": "20", "unit": "т", "destination": null}` | Из запроса не выводятся вид рыбы и адрес |
| Уточнения: список недостающих полей определяет код, LLM формулирует вопросы по списку; известное не переспрашивается; после ответа — обновление состояния, не подбор с нуля | Р3.2 | недостаёт `destination` → один вопрос | Вопросы соответствуют недостающим полям |
| Подбор: фильтрацию делает код (по каталогу, объёму, остатку), LLM ранжирует и объясняет; для 20 позиций поисковая инфраструктура не нужна | Р3.4 | код: 3 кандидата → LLM: объяснение выбора | В тексте только ID из отфильтрованных |
| Достоверность: связка «утверждение → запись/поле источника → версия материала»; проверка существования `product_id` не доказывает достоверность текста — соответствие формулировок источникам проверять и вручную по рубрике | Р3.5 | «гарантия года» без источника → вырезается | Неподтверждённые утверждения не проходят |
| Числа и фиксированные условия — из проверенных данных; LLM — объяснение выбора и связный текст | Р3.5 | суммы из результата Р2 | Суммы в тексте = суммы в DOCX = расчёт |
| DOCX: docxtpl — кандидат (плейсхолдеры `{{...}}` в болванке ещё не подтверждены как совместимые); согласовать имена полей с контрактом, повторяемые товарные строки вместо фиксированных трёх, обработка спецсимволов, обнаружение незаполненных обязательных плейсхолдеров | Р3.6 | цикл `{% for item in items %}` в шаблоне | Приёмка: 1 позиция, >3 позиций, длинные названия, разные ставки НДС, без кейса — и содержимое, и отрисованные страницы |
| Служебная сводка — отдельный шаблон, собирается из того же результата расчёта и источников | Р3.7 | сводка не входит в клиентский DOCX | Сводка доступна отдельно |

### Входы и выходы
- **Входы:** профиль компании (Р4), результат подбора и потребности (контракты Р1), результат расчёта (Р2).
- **Выходы:** промпты и модули извлечения/подбора; шаблон DOCX; сборщик документа; сводка; технические примеры КП для Р5.
- **До готовности ядра Р2:** работает от заглушки расчёта с фиксированными суммами (недели 1–3).

### Приёмка роли
Суммы в тексте и DOCX совпадают с результатом расчётного ядра; документ редактируется и читается; существенные утверждения имеют источники и соответствуют им; неподтверждённые условия остаются вопросами для уточнения. Проверяет: Р4 (по рубрике) и Р1.

## 4. Р4 — Данные и оценка качества

### Цель роли
Воспроизводимые профили компаний, тестовые запросы с критериями, независимые расчётные эталоны и отчёт о качестве — включая проверку метрики 80% и сравнение с обычным запросом к модели.

### Границы
- **Делает:** датасеты, контрольные запросы, эталоны, рубрики оценки, отчёт.
- **Не делает:** разработку ядра (Р2) и генерацию КП (Р3) — оценивает их, будучи независимым проверяющим.
- **Принцип независимости:** эталоны и критерии создаются до прогона и не подгоняются под результат.

Для воспроизводимости сохраняются: запросы, версии материалов, идентификатор модели, исходные ответы, заполненные рубрики |

| Заранее определить, какие запросы «полные», чтобы неудобные неуспехи не исключались из знаменателя метрики 80% | Р4.10 | список полных запросов зафиксирован до прогона | Знаменатель не меняется после прогона |
| Оценка: бинарные критерии для условий и структуры; время, число действий и ручных правок — измерения, не шкалы | Р4.8 | чек-лист «да/нет» по каждому критерию | Две независимые оценки сохранены, разногласия описаны |

| Сравнение с базовым LLM: сохранять модель, версии материалов, запросы, исходные ответы, заполненные рубрики | Р4.9 | папка прогона с артефактами | Сравнение воспроизводимо по сохранённым данным |

### Входы и выходы
- **Входы:** форматы контрактов (Р1), работающее ядро (Р2) и сценарий (Р3) — для оценки; тема учебной компании (решение команды, неделя 1).
- **Выходы:** два профиля; набор запросов с критериями; эталоны; рубрика; отчёты сравнения и качества.
- **Важно про метрику 80%:** состав финального набора фиксируется заранее так, чтобы полных запросов в нём было достаточно для осмысленной проверки порога. Отказы на поддерживаемых запросах не считаются успехами.

### Приёмка роли
Можно воспроизвести расчёты и оценку от данных до отчёта; отдельно посчитаны точность расчётов, качество полных запросов и корректность обработки проблемных. Проверяет: Р1 и второй участник (двойная оценка).

## 7. Контроль типовых ошибок декомпозиции

Перед стартом и на каждом еженедельном ревью тимлид проверяет:

- [ ] **Нет двух владельцев одного компонента** — «Р1 и Р5 отвечают за упаковку» заменяется одним владельцем и отдельным проверяющим.
- [ ] **Нет задач без выхода** — «изучить промпты» заменяется на конкретный сценарий, набор примеров и критерии.
- [ ] **Нет работы по очереди** — каждый имеет тестовые входы и заглушки, чтобы не ждать чужих компонентов.
- [ ] **QA не в конце** — критерии и эталоны готовы до итогового прогона.
- [ ] **Нет необоснованного расширения** — веб-интерфейс, CRM, отдельный платный API, MCP добавляются только при необходимости.
- [ ] **Есть временная оценка** — после распределения каждый участник оценил свои задачи с учётом реальной доступности; число людей само по себе не подтверждает выполнимость срока.
- [ ] **Неизвестные детали клиентского API оформлены вопросами** — их закрывает Р1 на неделе 1, а не заполняются догадками.
